Who / why

People who regularly check promotions and developers building rewards or personal-finance apps need current offer data in a usable format. Today they manually check merchant websites, read buried fine print themselves, or maintain separate scrapers for each source.

02 / Responsibility contract

Keep the agent on evidence

These are conceptual responsibilities for the proof of concept. The exact technical allocation belongs in the later spec.

01 / SOURCE INPUT

Collection layer

Retrieve public offer content and preserve its source link. Track each site independently so one failure does not erase successful results from elsewhere.

02 / AI AGENT

Extract, cite, abstain

Map page text to offer fields, attach supporting text to extracted details, and return “unknown” when the source does not establish a value.

03 / PRODUCT OUTPUT

Normalize and expose

Make consistent records available through the dashboard and API. Let the dashboard trigger a refresh and inspect collected details, evidence, and source failures.

GuardrailThe agent extracts public offer information; it does not determine personal eligibility, recommend cards, or initiate payments.
03 / API output

A record with its receipts

Illustrative shape only. The exact API contract and field names remain open for PRD and spec.

Each record should carry

The merchant and benefit, minimum spend, exclusions, activation requirements, expiration status, source link, and collection time. Source text is available for inspection so a user can see what supports the extracted details.

“Unknown” is a valid result, not a missing guess. Evidence should not be fabricated to make a record look complete.

{
  "merchant": "<merchant name>",
  "benefit": "<published reward or discount>",
  "conditions": {
    "minimum_spend": "<amount or unknown>",
    "exclusions": ["<published exclusions>"],
    "activation": "<requirement or unknown>"
  },
  "expiration": "unknown",
  "source_url": "<public offer page>",
  "collected_at": "<timestamp>",
  "supporting_text": [
    "<verbatim evidence from the source>"
  ]
}
04 / MVP boundary

Small enough to prove

One complete collection workflow is the finish line. Expand each boundary to review what belongs in this experiment.

Now / MVPPublic-source collection, structured output, inspectable evidence
  • Two or three publicly available US rewards or merchant offer websites.
  • AI-assisted extraction and normalization, with unpublished fields left unknown and known details traceable to source text.
  • A developer-consumable API as the main deliverable, plus a simple dashboard to refresh and inspect the workflow.
  • Per-source failure reporting while successful sources still return results.
LaterUseful extensions after the collection proof
  • Compare refreshes and highlight changed offers.
  • Expand the set of supported public sources.
  • Revisit personalized bank offers, eligibility matching, card recommendations, payment routing, or external partner API integrations as separate future work.
Cut / not this buildNo personalization, recommendations, or transaction actions

Personalized bank offers, eligibility matching, card recommendations, payment routing, and external partner API integrations are outside this proof of concept. They are not needed to prove public-page extraction and structured API delivery.

For later planning

Which public websites to support, what exact API contract to expose, and how evidence is attached to individual fields are still open. Resolve those in the PRD and technical spec rather than expanding this scope sketch.
